# Product decisions

Decisions by the project owner, recorded 2026-09-29. They apply to the current release (the go-live described in `docs/GO-LIVE.md`) unless stated otherwise.
Findings in `docs/FEEDBACK.md` refer to these by ID.

| ID | Decision | Consequence for this release | Findings |
|---|---|---|---|
| D-01 | **Roles:** in this release only administrators use the web panel. Beekeeper and wholesaler logins are deferred to a later release. | No role-based feature work. The existing `[Authorize(Roles="Administrator")]` model stays. A non-admin who logs in gets a clear message instead of an AccessDenied loop. | FB-33 (deferred), FB-02 |
| D-02 | **Public self-registration is closed.** Only admins create users; `UserManagement/Create` stays. | Remove the Register page, the POST action and the "Sign up" links. | FB-02 |
| D-03 | **Beekeeper e-mails:** beekeepers do not log in, so placeholder e-mails (`{businessNo}@top4honeychains.com`) are acceptable for now. Password reset must work for admin accounts with real e-mails. | Fix and verify the forgot/reset flow for real addresses; no change to beekeeper e-mails. | FB-01 |
| D-04 | **Beekeepers and apiaries are deactivated, never deleted** (traceability). | No delete function. The UI must say clearly that deactivation replaces deletion and what it does. | FB-08, FB-14, FB-07, FB-13 |
| D-05 | **Final-production rule stays:** a raw lot is eligible only when all its CCP checks are completed. | The UI must show which lots are not eligible and which CCP checks are missing. | FB-20 |
| D-06 | **Raw honey rules unchanged:** no change and no DB change in this release. | The partner's question goes to `docs/PARTNER-QUESTIONS.md` (PQ-01). | FB-16, FB-17 (deferred) |
| D-07 | **Deferred features:** map-based location picking and CCP images are postponed to a later release. | Not implemented now. | FB-09, FB-27 (deferred) |
| D-08 | **Lookup fields stay but are optional:** education level, beekeeping purpose type and beekeeping type. | Make them clearly optional in the beekeeper forms. No DB change: the FK columns are already nullable. | FB-06 |
| D-09 | **Non-admin accounts are locked out** (follows from D-01). Beekeeper logins used the business number as the password, which is guessable. | (a) New beekeeper accounts get a random, never-shown password. (b) `db/migrations/001_lock_out_non_admin_accounts.sql` locks out every account outside the Administrator role at go-live (Identity lockout, security stamp rotated). New beekeeper accounts are also locked at creation, and **Activate** no longer unlocks a beekeeper's login; Deactivate still locks it (confirmed by the owner 2026-09-29). | ENG-06 |
| D-10 | **Upload limits** (confirmed by the owner 2026-09-29). Images (beekeeper profile photo, apiary photos): JPG, PNG or WEBP, at most 8 MB and 10000 px per side. CCP content videos: MP4 or WEBM, at most 25 MB. | Enforced server-side (extension plus file signature). 25 MB stays below the default request limits of Kestrel (about 28.6 MB) and IIS (30,000,000 bytes), so no server change is needed. Larger videos would need a higher limit here and in IIS (`requestLimits maxAllowedContentLength`). | FB-26, ENG-10 |
| D-11 | **QR codes contain the full public URL** (`App:PublicBaseUrl` + `/honeystory/{guid}`). No labels have been printed yet. | `/honeystory/qrcode` renders only the URL of an existing batch (unknown or invalid codes: 404). `App:PublicBaseUrl` is required in production. | GO-LIVE |
| D-12 | **HoneyStory privacy.** Draft/unfinished batches are not public (404). Published batches show the beekeeper's name but not the photo or phone. Apiary locations are shown only approximately (district/province level, no exact GPS pin). | Implemented as: coordinates rounded server-side to 0.1° (about 10 km, roughly district level) and drawn as an area without a pin, map zoom capped; apiary photos served only for apiaries of finalized batches. Showing district/province *names* would need reverse geocoding (another Google API on the key) and is not done. | GO-LIVE |
| D-13 | **HTTPS:** the certificate and binding are handled on IIS by the university IT; the app enables HTTPS redirection and HSTS in Production only. | `UseHsts` + `UseHttpsRedirection` when `ASPNETCORE_ENVIRONMENT=Production`; IT request in `docs/GO-LIVE.md`. Verified with a local Production run: HTTP → 307 to HTTPS, HSTS header on HTTPS (not sent for `localhost`, by design), Development unchanged. | GO-LIVE |
| D-14 | **Finalized batches are permanent and locked** (owner request 2026-10-03, see `docs/CCP-CURRENT.md`). | Server-side: after finalize, the batch data, its composition, its CCP assignments and its CCP values cannot be changed or deleted; the same applies to every raw lot used in a finalized batch. The pages are read-only with a lock message. **Unfinalize was removed** (it would undo the lock); a correction needs a new batch. A CCP assignment that has values or a "Not applicable" record cannot be removed (also on drafts), so logged values are never lost. | CCP-01, CCP-02 |
| D-15 | **"Not applicable" CCP status** (owner request 2026-10-03). | Status 5 with a mandatory reason, the user name and the time (DB check constraint). Allowed only while the CCP has no values and the record is not locked; it can be removed again before the lock. Counts as done for eligibility and finalize. Shown as "Not applicable" with the reason (not the user) on Honey Story. | CCP-03 |
| D-16 | **Finalize rule** (owner request 2026-10-03). | A batch can be finalized only when every CCP that applies to batches is assigned and Completed or Not applicable, and every lot in it still has at least one CCP and all of them Completed or Not applicable (as D-05). ManageBatch lists what is missing. The five batches finalized before this rule (ids 2–6) are **not changed**; Honey Story shows their missing CCPs as "Not recorded". | CCP-04 |
| D-17 | **CCP applicability is data** (owner request 2026-10-03). | `CriticalControlPoints.AppliesTo` = RawLot / Batch, seeded CCP 0–3 = RawLot, CCP 4–10 = Batch, required on the CCP form. Assignment pages offer, and the server accepts, only applicable CCPs. Honey Story no longer uses hard-coded CCP ids. | CCP-05 |
| D-18 | **Parameter metadata and limits** (owner request 2026-10-03). | Data type (Number / Yes-No / Text / File), unit, default min/max, required flag, limit note/source and a "verified" flag; honey-class limits (Floral / Honeydew / Pine, set on the honey type), conditional limits (diastase min 3 when HMF ≤ 15) and sum limits (fructose + glucose) in `CriticalControlPointParameterLimits`. Seeds from the Turkish Food Codex are marked **to verify**. An in-range flag and the applied limit are stored on save (not recalculated when limits change) and shown red/green on the CCP pages. **Honey Story shows compliance only for parameters whose limits are marked verified** (unverified seeds could wrongly brand honey as non-compliant in public); for values recorded before this release it is computed at display time. Completion now needs only the required parameters. | CCP-06 |
| D-19 | **File values for CCP parameters** (e.g. lab reports). | PDF up to 10 MB, or JPG/PNG/WEBP up to 8 MB (D-10 image rules), checked by extension and file signature. Stored under `App_Data/ccp-files/` (outside `wwwroot`) and downloadable by administrators only; Honey Story shows "document on file", never the file. | CCP-06 |
| D-20 | **Public free text per CCP** (owner request 2026-10-03, follows D-12). | `CriticalControlPoints.PublicTextValues`: when off, Honey Story shows only the status and Yes/No and numeric results of that CCP; free-text answers and files are left out entirely. Off for CCP 0 (field audit at the beekeeper: answers may contain personal data or locations), on for CCP 1–10 (they showed text before); off by default for new CCPs. Files are never published (D-19). | CCP-07 |
| D-21 | **Honey-type exceptions and ratio checks** (owner request 2026-10-03). | A limit row can target one honey type (beats the honey class): chestnut honey follows the honeydew rule for electrical conductivity (min 0.8 mS/cm). A limit row can be a ratio check (value / other value) evaluated in addition to the main limit: fructose/glucose 0.9–1.4 for floral honey. The pine 23 % moisture seed is noted as doubtful (EU 2001/110: the 23 % exception is for heather). All "to verify" (PQ-03). | CCP-08 |
| D-22 | **Organization model** *(confirmed 2026-10-03, revisable)*: organizations with capabilities, users joined through memberships with org roles, replacing global roles for business access. | Design in [ROLE-MODEL.md](ROLE-MODEL.md). | D-40 | **P2 implementation choices** *(our choices, revisable)*. | (a) The CCP responsibility matrix (D-25) is in `CcpResponsibilities` / `…Capabilities` / `…Roles`, seeded by CCP code (CCP 0: the beekeeper's association, FieldInspector enters; CCP 1: Processing, SampleAcceptanceOfficer or Staff; CCP 2–6: Processing; CCP 7–9: Packing; CCP 10: Wholesale, Retail or Packing; Staff enters, QualityApprover approves) and editable at `/CcpResponsibilities`. (b) A lot or batch belongs to `OwnerOrgId`, or, when empty, to the organization created from its wholesaler (D-36). An org reads a CCP it is responsible for, the earlier CCPs of the same item, and the lots of its own batches; it never sees other orgs' items (404). (c) With the flag on, complete values are **Submitted** (status 6) until a second person approves; only approved (or exempt) CCPs count as done for lot eligibility and finalize. A save without changes keeps the approval. (d) Platform administrators keep the master data until P3 intake (lots, batches, composition, CCP assignment, owning org) but are read-only on CCP values, approvals and finalize; a value change is a correction record applied only when a second administrator approves it, also on finalized items (D-35). (e) Members finalize their own batch: Staff or OrgAdmin requests, a QualityApprover (another person, or the same person under the exemption, flagged `SelfFinalized`) confirms. (f) A configured central association can also read and list the associations it verifies. | D-25, D-27, D-35, D-36 |
| D-41 | **P3 implementation choices** *(our choices, revisable)*. | (a) **Intake**: the SampleAcceptanceOfficer of a verified Processing org finds the beekeeper by exact business or verified registry number (no browsing of beekeepers) and records apiary, honey type, period, date, quantity, province/district and the delivery-form photo (PDF/JPG/PNG/WEBP, `App_Data/intake-forms/`, SHA-256). The intake creates the raw lot owned by that org (`OwnerOrgId`; wholesaler = the org's legacy wholesaler, if any) and assigns every raw-lot CCP. SMS goes through `ISmsSender`; the current implementation only logs a masked number (status `Logged`, or `NoPhoneNumber`). (b) **Custody**: the batch owner holds the whole batch; only finalized batches ship; Staff or OrgAdmin of a verified holder ships to another verified org; the quantity is reserved at once and moves on receipt; the receiver's Staff/OrgAdmin confirms or rejects with a reason (rejected quantity returns). Partial shipments are allowed; parallel shipments of one batch are serialized. (c) **CCP 10 per holder**: each later holder records storage for the quantity it holds (`HolderStorageRecords`), with the matrix capabilities and roles of CCP 10 and four-eyes approval; the owner's CCP 10 stays on the batch. Later holders read the batch CCP records, not the lots. (d) **Recall report**: platform administrators see everything (read-only); the batch owner sees lots, beekeepers and intake forms and its own shipments; other holders see only their shipments and holdings; the beekeeper's association sees its member's lot without the intake form; everything else is counted as "not shown". Printable page and CSV (UTF-8, formula-safe). | D-26, D-36 |
| D-42 | **P4 implementation choices** *(our choices, revisable)*. | (a) **Samples**: the SampleAcceptanceOfficer of the lot's owner takes the sample right after intake (or later): seal number, counter-sample seal (different), storage place and retain-until date, and a verified Laboratory org; `SampleCustodyEvents` records sent / received / rejected. The lab's Analyst or LabManager records receipt; a broken seal rejects the sample with a reason and is flagged. (b) **Results**: only for a received sample; the Analyst enters CCP 1 parameters (metadata and limits as on the CCP page), uploads the report PDF (SHA-256 stored, `App_Data/lab-reports/`) and submits; the LabManager approves or returns with a reason. **Four-eyes without exemption** (approver ≠ the person who entered or submitted; also a DB check). Approval re-hashes the stored file and refuses a mismatch, and is refused for a lot locked in a finalized batch. (c) Approved results become the lot's CCP 1 values with `LabReportId`; the CCP page skips them on save and shows them read-only; only a correction record (D-35) changes them. The CCP is approved by the LabManager when all its values come from approved reports, else Submitted for the producer. (d) **In-house lab** = the lab org is the lot's owning org (snapshot at approval); accreditation (Laboratory capability, accredited, not expired) is also a snapshot. (e) **Honey Story badges**, flag on only, from approved reports of verified labs: "tested by an accredited lab" (every lot), "in-house lab", "all control points approved" (no finalize blocker), "within verified limits" (at least one verified-limit value and all within; none today because no limit is verified yet, D-18); report codes link to the public **verify page** (`/verify-report`, code → status, lab, accreditation, report number, SHA-256; drafts hidden; no lot, beekeeper or user data; a PDF can be compared in the browser). (f) Automated tests: `TOP4HoneyChains.Web.Tests` (xUnit, `dotnet test`), first covering the P3 shipment rule. | D-27, D-35, D-18 |
| D-43 | **P5 implementation choices** *(our choices, revisable)*. | (a) **Consent**: the OrgAdmin of the beekeeper's verified association records it (date, signed document stored with SHA-256 in `App_Data/consents/`, consent text version and hash, "name may be shown" choice); one active consent per beekeeper; withdrawal (optional reason) unpublishes at once; platform administrators read only. The consent text is a placeholder until the KVKK wording is confirmed (PQ-09). (b) **Storefront** `/storefront/{code}`: the code is random (`BK-` + 8 characters), never derived from the name, and kept across consents. Public only while the beekeeper is active, the registry number is verified, the current association is verified and has the active consent. Shows the name only with consent (else the code), province from the verified registry number's plate code and district from the intakes until PQ-12 is decided, honey types and number of lots in finalized batches, approved lab reports of verified labs, links to those batches' Honey Story pages, the association; never phone, photo, birth date, business number or location. Printable card with a QR code (`/storefront/{code}/qr`). Honey Story links to published storefronts. (c) **Origin**: `RawHoneyProductions.OriginCountry` (ISO alpha-2), chosen at intake and on the lot forms with the flag on; existing lots stay NULL and count as TR, new lots default to TR. At finalize (both finalize paths, also with the flag off, invisible there) `BatchOriginShares` stores the shares by weight with two decimals adding up to exactly 100 (largest remainder); Honey Story shows them largest first, and computes them for batches finalized earlier. Display and rounding still open (PQ-11). | D-30, D-31 |
| D-44 | **Role-based start page and process flow** *(assumption taken while the owner was away, revisable)*. | With the flag on, every user lands on "İşlerim" (`/MyWork`) after login, platform administrators included (with the flag off: Dashboard as in v1.0).
